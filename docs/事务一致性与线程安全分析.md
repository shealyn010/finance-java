# 事务一致性与线程安全分析

## 一、发现的问题

### 问题 1: COUNT 缓存竞态条件
**位置**: `WorkOrderService.countCache`
**风险**: 高

```java
// 问题代码
if (System.currentTimeMillis() - countCacheTime > 60000) {
    countCache.clear(); // 线程A和B同时进入,重复clear
    countCacheTime = System.currentTimeMillis();
}
```

**修复方案**: `synchronized` 块保护 clear 操作,或直接用 Caffeine Cache 的 `expireAfterWrite`。

### 问题 2: MQ 消息可靠性
**位置**: `WorkOrderService.createAsync()` → RabbitMQ → `OrderCreateConsumer`
**风险**: 高

```
createAsync → rabbitTemplate.send → 消息进队列(成功)
                                    ↓
                            Consumer 消费
                                    ↓
                            workOrderMapper.insert → 失败(DB挂了)
                                    ↓
                            消息丢失! RabbitMQ已ACK
```

**修复方案**: 手动 ACK + 死信队列重试：
```java
@RabbitListener(queues = "order.create", ackMode = "MANUAL")
public void onMessage(String json, Channel channel, Message msg) {
    try { workOrderService.createDirect(order); channel.basicAck(tag, false); }
    catch { channel.basicNack(tag, false, true); } // 重回队列
}
```

### 问题 3: StringBuilder 线程不安全
**位置**: `AgentChatService.context`
**风险**: 低（实际不会多线程同时操作同一用户上下文）

```java
// ConcurrentHashMap保护了Map,但StringBuilder.append不是原子的
context.compute(userId, (k, v) -> {
    v.append("用户: ").append(userMessage); // 两个线程同时append → 数据错乱
    return v;
});
```

**修复方案**: 用 `StringBuffer`（线程安全）或加 `synchronized`。

## 二、当前的事务边界

| 操作 | 事务范围 | 是否安全 |
|------|---------|---------|
| 工单创建(Direct) | 单条INSERT,MyBatis自动提交 | ✅ 原子 |
| 工单创建(Async) | MQ投递 + 消费者INSERT | ❌ 跨进程不一致 |
| 批量生成 | 多线程各INSERT各的 | ⚠️ 批次间无事务 |
| AI分析更新 | 单条UPDATE | ✅ 原子 |

## 三、分布式场景下的升级方案

### Seata AT 模式（适合已有项目低侵入）
```java
@GlobalTransactional
public WorkOrder create(WorkOrder order) {
    workOrderMapper.insert(order);           // RM1: MySQL
    rabbitTemplate.send("order.create", msg); // RM2: MQ(需要支持事务消息)
    // 任一失败 → Seata自动回滚
}
```

### 事务消息（RocketMQ 原生支持）
```
半消息 → 执行本地事务 → commit/rollback
RabbitMQ 需自行实现：先写本地事件表 → MQ投递 → 确认后删事件
```

## 四、修复优先级

| 优先级 | 问题 | 方案 |
|--------|------|------|
| P0 | COUNT缓存竞态 | synchronized修复 |
| P0 | MQ消息可靠性 | 手动ACK+DLQ |
| P1 | StringBuilder | StringBuffer替换 |
| P2 | 分布式事务 | Seata/RocketMQ事务消息 |

## 五、面试视角

> "在高并发工单写入场景中，通过 synchronized 块保证 COUNT 缓存的一致性，MQ 采用手动 ACK + 死信队列确保消息不丢失。对于分布式事务，采用本地事件表 + 定时补偿的方案，避免引入重量级框架。
