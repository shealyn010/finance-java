# 隔离级别与分布式事务 —— 以 FinInsight 为例

> 当前 MySQL 隔离级别: `REPEATABLE-READ`（InnoDB 默认）

---

## 一、模拟攻击：用我们自己的 SQL 演示

先在 210 万数据上造三个并发场景，直接看结果。

### 场景1: 幻读 — COUNT 缓存和真实数据对不上

```sql
-- 时刻1: 查询A 翻页第1页, COUNT(*) = 2100000
SELECT COUNT(*) FROM work_order WHERE user_id=5;
-- 时刻2: 查询B 创建了5条新工单（另一个事务还没提交）
INSERT INTO work_order VALUES (...);
-- 时刻3: 查询A 翻第2页, WHERE order_time < 'xxx' LIMIT 30
-- 此时第2页可能包含时刻2新插入的行（如果插入的 order_time 比第1页最后一条更早）
-- 结果: 同一次"第1页+第2页"浏览中,第2页多出了5条重复,用户觉得数据乱了
```

**什么时候真会出问题**: 两个用户同时在列表页翻页 + 另一个人疯狂创建工单。

**我们项目怎么防护**: MySQL `REPEATABLE-READ` 下，查询A 读取的是事务开始时的快照，不会读到查询B 新插入的行。**但 COUNT 不走快照**——`COUNT(*)` 是当前读。

**修复**: COUNT 走快照需要开启 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

### 场景2: 不可重复读 — 同一行两次读到不同值

```sql
-- 查询A: 第1次读
SELECT profit FROM work_order WHERE order_id='xxx';  -- profit=500
-- AI分析B: 更新同一行
UPDATE work_order SET ai_category='高利润' WHERE order_id='xxx';
-- 查询A: 第2次读
SELECT profit FROM work_order WHERE order_id='xxx';  -- 在我这个事务里还是500 ✅
```

**REPEATABLE-READ 已经防了这个问题**——同一事务内两次读是一致的。

**但！`UPDATE ... SET profit=profit+100 WHERE id='xxx'` 如果两个事务同时执行，会丢失更新。**

### 场景3: 丢失更新 — 两个管理员同时改同一工单

```java
// 线程A: 更新状态为 completed
UPDATE work_order SET status='completed' WHERE order_id='wo001';

// 线程B: 更新状态为 closed（在线程A提交前就读到了旧值）
UPDATE work_order SET status='closed' WHERE order_id='wo001';
// 结果: 后提交的覆盖了先提交的，线程A的修改丢失
```

**我们项目当前的代码**:
```java
public WorkOrder updateStatus(String orderId, String status) {
    WorkOrder order = workOrderMapper.selectById(orderId); // 1. 读(旧值)
    order.setStatus(status);
    workOrderMapper.updateById(order);                      // 2. 写(可能覆盖别人)
    return order;
}
```

这是**经典的 Read-Modify-Write 竞态**——没有乐观锁。

**修复**: 加 `version` 字段或 `UPDATE ... WHERE status='旧的status'`。

## 二、分布式事务问题

### 问题1: MQ + DB 不是原子的

```
createAsync()
  ├── rabbitTemplate.send(msg)     → 成功
  └── 返回 order（还没真正写DB）
        │
        消费者 consume(msg)
          └── workOrderMapper.insert → 失败(DB挂了)
                │
                消息已ACK，但数据丢了 ❌
```

**我们的修复（手动ACK）只能解决一半**——消费失败重试。但如果 "MQ投递成功 + 消费者还没来得及ACK就崩溃"，消息会重回队列被再次消费，可能重复写入。

**正确方案——本地事件表**:

```sql
CREATE TABLE outbox (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_type VARCHAR(50),     -- 'ORDER_CREATED'
    payload TEXT,               -- JSON
    status ENUM('pending','sent') DEFAULT 'pending'
);

-- 同一个本地事务内:
INSERT INTO work_order VALUES (...);
INSERT INTO outbox VALUES ('ORDER_CREATED', '...');  -- ← 和上面同一个事务!

-- 定时任务扫 outbox, 投递MQ
SELECT * FROM outbox WHERE status='pending';
-- 投递成功 → UPDATE status='sent'
```

### 问题2: Redis 缓存与 DB 不一致

```
创建工单 → @CacheEvict 清缓存 → 缓存空了
                                 ↓
                            查询来了 → 查DB → 写Redis (TTL 30min)
                                 ↓
                            但如果此时DB还没提交呢？
                                 ↓
                            缓存了未提交的数据 → 回滚后缓存是脏的 ❌
```

**修复**: 在事务提交后清缓存（`@TransactionalEventListener`）。

### 问题3: AI 分析更新 + 统计物化视图

```
AI分析:
  UPDATE work_order SET ai_category='高利润' WHERE id='xxx';  → 成功
  -- 下面这行不是同一个事务:
  物化视图work_order_report需要刷新 ... → 忘记刷新/刷新失败

结论: 物化视图落后于真实数据
```

**修复**: 定时刷新物化视图，或通过 Binlog 增量更新。

## 四、修复编码示例

### 修丢失更新（乐观锁）

```java
public WorkOrder updateStatus(String orderId, String status) {
    // 方案A: CAS更新
    int rows = workOrderMapper.updateStatusCAS(orderId, status);
    if (rows == 0) throw new BizException(409, "工单已被其他人修改,请刷新重试");
    return workOrderMapper.selectById(orderId);
}

// Mapper:
@Update("UPDATE work_order SET status=#{status} WHERE order_id=#{id} AND status != #{status}")
int updateStatusCAS(String id, String status);
```

### 修缓存事务边界

```java
@TransactionalEventListener(phase = AFTER_COMMIT)
public void onOrderCreated(WorkOrder order) {
    // 事务提交后清缓存,确保不会缓存未提交数据
    redisTemplate.delete("fin:report::typeStats_" + order.getUserId());
}
```

### 修分布式锁接入

```java
// 创建工单防重复提交
if (!distributedLock.tryLock("order:" + order.getCustomer(), 0, 5, () -> true)) {
    throw new BizException(429, "5秒内请不要重复提交");
}
```
